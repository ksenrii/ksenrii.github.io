TLS

TLS（Transport Layer Security，传输层安全协议）是现代互联网中最重要的安全协议之一。我们平常访问的 HTTPS、登录网页、在线支付、接口鉴权、移动应用通信，背后大多都依赖 TLS 来保证通信的机密性、完整性和身份认证。

TLS 并不是单一的加密算法，而是一套协议体系。它结合了非对称加密、对称加密、消息认证码、数字证书、密钥交换等多种密码学机制，解决“如何在不可信网络上安全通信”这个核心问题。

概述

TLS 的主要目标有三个：

  1. 机密性：防止第三方看到通信内容；
  2. 完整性：防止数据在传输过程中被篡改；
  3. 身份认证：确认对方确实是你想连接的服务器，必要时也可验证客户端身份。

在实际使用中，TLS 最常见的场景就是 HTTPS。HTTP 本身是明文协议，而 HTTPS 本质上就是在 HTTP 外层套了一层 TLS。

从协议演化上看，TLS 可以理解为 SSL 的继任者。早期有 SSL 2.0、SSL 3.0，后来逐步发展为 TLS 1.0、TLS 1.1、TLS 1.2，再到目前更推荐使用的 TLS 1.3。

TLS 的基本组成

TLS 主要由以下几部分构成：

  • 握手协议（Handshake Protocol）：协商版本、密码套件、密钥，并完成身份认证
  • 记录协议（Record Protocol）：负责将上层数据切分、加密、完整性校验后发送
  • 告警协议（Alert Protocol）：在出现错误或连接关闭时传递告警信息
  • 变更密码规范协议（Change Cipher Spec）：用于通知后续开始使用协商好的加密参数

其中，最关键的是 握手协议。握手阶段完成之后，双方才会进入加密通信阶段。

TLS 的核心目标

TLS 要解决的问题，可以概括为下面这句：

在一个任何人都能监听的网络上，如何安全地建立一条只有通信双方能理解的信道。

为此，它通常需要完成：

  • 协商使用哪种密码套件；
  • 服务器向客户端证明自己的身份；
  • 生成双方共享的会话密钥；
  • 之后用对称加密高效传输数据。

这里的设计思路很典型：

  • 握手阶段使用非对称密码学来完成身份确认和密钥交换；
  • 数据传输阶段使用对称密码学来提高效率。

这是因为非对称加密虽然安全性和灵活性更强，但计算开销较大；而对称加密速度更快，更适合大量数据传输。

TLS 握手流程

下面以最常见的 TLS 1.2 / TLS 1.3 思想来理解握手过程。

1. 客户端发起连接

客户端首先向服务器发送 ClientHello，里面通常包含：

  • 支持的 TLS 版本
  • 支持的密码套件
  • 随机数 ClientRandom
  • 扩展信息，例如 SNI、ALPN、支持的椭圆曲线等

这一阶段的作用是告诉服务器：

“我能支持什么，你看看你选哪个。”

2. 服务器响应

服务器收到后，返回 ServerHello，并给出：

  • 选择使用的 TLS 版本
  • 选择的密码套件
  • 随机数 ServerRandom
  • 服务器证书
  • 必要时还会发送密钥交换参数

如果服务器需要客户端证书认证，也会在这里请求客户端证书。

3. 验证服务器证书

客户端会检查服务器证书是否可信，通常包括：

  • 证书是否过期
  • 域名是否匹配
  • 证书链是否能追溯到受信任的根证书
  • 证书是否被吊销（视实现而定）

如果证书验证失败，客户端通常会直接中断连接。

4. 密钥交换

握手中最关键的一步，是让双方在不安全网络上协商出一个共享密钥。

在旧版本 TLS 中，常见做法是使用 RSA 直接加密预主密钥（Pre-Master Secret）。
而在现代 TLS 中，更常见的是使用 (EC)DHE 进行密钥交换。

其核心思想可以写成：

\[ \text{shared secret} = f(\text{client private}, \text{server public}) \]

但这个共享秘密不会直接作为通信密钥，而是进一步经过密钥派生函数（KDF）生成会话密钥。

5. 派生会话密钥

握手双方会基于共享秘密、ClientRandom、ServerRandom 等信息，使用密钥派生算法生成后续通信所需的密钥材料，例如：

  • 客户端写入密钥
  • 服务器写入密钥
  • 初始化向量（IV）
  • 完整性校验密钥

TLS 1.2 和 TLS 1.3 在具体派生方式上有所不同，但核心思想一致：
不要直接把共享秘密拿来用，而是通过 KDF 派生出多个用途明确的密钥。

6. 握手完成

双方在确认握手消息无误后，会发送 Finished 报文。这个报文中包含握手摘要的校验值，用于证明：

  • 前面的握手消息没有被篡改；
  • 双方对握手内容的理解一致；
  • 后续开始使用协商好的加密参数。

此后，连接正式进入加密数据传输阶段。

TLS 1.2 与 TLS 1.3 的区别

TLS 1.3 相比 TLS 1.2 做了很大的简化和增强，主要体现在：

  • 握手轮次更少，延迟更低
  • 删除了很多不安全或过时的算法
  • 强制使用前向安全性更好的密钥交换方式
  • 加密范围更大，安全性更强
  • 握手逻辑更清晰

TLS 1.2 的特点

TLS 1.2 仍然支持较多旧算法，例如：

  • RSA 密钥交换
  • CBC 模式加密
  • 一些旧的哈希和签名算法

虽然它仍然广泛使用，但安全性和协议复杂度都不如 TLS 1.3。

TLS 1.3 的特点

TLS 1.3 的设计目标之一就是“减法”：

  • 去掉不安全的历史包袱
  • 强制使用更现代的密码套件
  • 默认使用前向安全的密钥交换
  • 将握手流程简化为更少的消息往返

这使得 TLS 1.3 不但更安全，而且更快。

TLS 中的密码学组件

TLS 并不是单独依赖某一种算法，而是组合使用多种密码学原语。

非对称加密 / 密钥交换

常见用于握手阶段：

  • RSA
  • Diffie-Hellman
  • ECDHE

其中，现代 TLS 更推荐 ECDHE，因为它通常具有更好的性能和前向安全性。

对称加密

用于后续数据传输，常见有：

  • AES-GCM
  • ChaCha20-Poly1305

它们既能提供加密，又能提供认证，属于 AEAD（Authenticated Encryption with Associated Data）方案。

哈希与消息认证

TLS 需要对握手和记录进行完整性校验，常用：

  • SHA-256
  • SHA-384
  • HMAC

在现代 TLS 中，很多完整性校验已经由 AEAD 模式统一解决。

为什么 TLS 需要证书

如果没有证书，客户端无法确认“你连到的服务器到底是谁”。

假设攻击者伪装成银行服务器，客户端如果没有验证身份，就可能把密码、验证码、银行卡信息发送给攻击者。

证书的作用就是：

  • 证明服务器身份；
  • 把服务器公钥和域名绑定；
  • 由可信的 CA（证书颁发机构）进行背书。

因此，证书机制是 TLS 身份认证的关键。

一个简化的 TLS 流程示意

可以把 TLS 看成下面这个过程：

  1. 客户端发起 ClientHello
  2. 服务器返回 ServerHello 和证书
  3. 客户端验证证书
  4. 双方完成密钥交换
  5. 双方派生会话密钥
  6. 后续数据用对称加密传输

安全性分析

TLS 的安全性来源于多个层面：

  • 证书体系确保你连的是正确的服务器；
  • 密钥交换确保窃听者无法得到会话密钥；
  • 对称加密确保消息内容不可读；
  • 认证加密确保消息未被篡改；
  • 前向安全性确保即使未来服务器私钥泄露，历史会话也不一定能被解密。

其中，前向安全性是现代 TLS 非常重要的特性。
如果使用静态 RSA 密钥交换，服务器私钥一旦泄露，过去抓到的通信流量就可能被解密。
而使用 ECDHE 时，每次会话都会生成临时密钥，即使长期私钥泄露，历史会话也更难被恢复。

TLS 的实际应用场景

TLS 几乎已经是互联网基础设施的一部分，常见于：

  • 网页访问（HTTPS）
  • API 接口通信
  • 邮件传输
  • 即时通信
  • VPN
  • 云服务 API
  • 物联网设备通信

也就是说，只要你看到地址栏里有小锁图标，或者客户端和服务器之间要传敏感信息，TLS 往往就在发挥作用。

一个简单的 OpenSSL 示例

下面给出一个最基础的命令行示例，用来查看网站的证书和握手信息：

openssl s_client -connect example.com:443 -servername example.com
